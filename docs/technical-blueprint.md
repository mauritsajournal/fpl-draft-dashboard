## 1. Architecture Overview

The system consists of two distinct pipelines: a **data pipeline** (GitHub Actions) that fetches and transforms FPL Draft API data into static JSON files, and a **presentation layer** (Astro static site) that renders those JSON files into an interactive dashboard deployed on GitHub Pages.

```
┌─────────────────────────────────────────────────────────────────┐
│                     GitHub Repository                           │
│                                                                 │
│  ┌──────────────────┐    ┌──────────────┐    ┌───────────────┐ │
│  │  GitHub Actions   │    │  data/*.json  │    │  Astro Site   │ │
│  │  (Scheduled Cron) │───>│  (committed)  │───>│  (SSG Build)  │ │
│  └────────┬─────────┘    └──────────────┘    └───────┬───────┘ │
│           │                                          │         │
│           │                                          ▼         │
│           │                                  ┌───────────────┐ │
│           │                                  │ GitHub Pages   │ │
│           │                                  │ (Static HTML)  │ │
│           │                                  └───────────────┘ │
│           │                                          │         │
└───────────┼──────────────────────────────────────────┼─────────┘
            │                                          │
            ▼                                          ▼
   ┌─────────────────┐                        ┌──────────────┐
   │ FPL Draft API    │                        │ User Browser │
   │ (draft.premier   │                        │ (Dashboard)  │
   │  league.com/api) │                        └──────────────┘
   └─────────────────┘
```

**Data Flow:**
1. GitHub Actions cron job triggers every 6 hours (at 01:00, 07:00, 13:00, 19:00 UTC — offset from typical PL kickoff times to avoid API instability during live matches)
2. Node.js fetch scripts call FPL Draft API endpoints (server-side, no CORS issue)
3. Incremental fetch: only new/changed gameweek data is fetched, tracked via `data/meta.json`
4. Raw API responses are validated and transformed into dashboard-optimized JSON structures
5. Changed JSON files are committed to `data/` directory
6. **Single combined workflow:** After committing data, the same workflow builds the Astro site and deploys to GitHub Pages (avoids the GITHUB_TOKEN limitation where commits from Actions don't trigger other workflows)
7. Astro reads JSON files at build time, generates static HTML/JS
8. Users visit the dashboard — all data is pre-rendered, charts hydrate client-side

## 3. Component Design

### 3.1 Data Pipeline (`scripts/`)

- **Responsibility:** Fetch all FPL Draft API data, transform into dashboard-ready JSON, commit to repo
- **Inputs:** FPL Draft API HTTP responses + `data/meta.json` (fetch state tracking)
- **Outputs:** JSON files in `data/` directory
- **Dependencies:** Node.js fetch API, FPL Draft API
- **Trigger:** GitHub Actions cron (every 6 hours) or manual dispatch

**State tracking:** `data/meta.json` tracks the last successfully fetched gameweek for picks and live data. This enables incremental fetching — only new gameweeks are fetched, and completed GW data is never re-fetched.

```typescript
interface FetchMeta {
  lastFetchedGameweek: number;  // Last fully completed GW we have picks/live data for
  lastUpdated: string;          // ISO timestamp of last successful fetch
  currentSeason: string;        // "2025-26"
  draftFetched: boolean;        // Draft choices only need fetching once
}
```

**Fetch scripts:**

| Script | API Endpoint(s) | Output File(s) | Verified |
|--------|-----------------|----------------|----------|
| `fetch-bootstrap.ts` | `GET https://draft.premierleague.com/api/bootstrap-static` | `data/players.json` (all players with stats incl. xG, xA) | Yes - returns `{elements: [...]}` with 700+ player objects |
| `fetch-league.ts` | `GET https://draft.premierleague.com/api/league/820/details` | `data/league.json` (league info, entries, matches, standings) | Yes - returns `{league, league_entries, matches, standings}` |
| `fetch-element-status.ts` | `GET https://draft.premierleague.com/api/league/820/element-status` | `data/ownership.json` (who owns which player) | Yes - returns `{element_status: [...]}` with owner field |
| `fetch-picks.ts` | `GET https://draft.premierleague.com/api/entry/{id}/event/{gw}` for all 8 entries x **new** GWs only | `data/picks/gw{XX}.json` (per-GW picks for all 8 entries) | Yes - returns `{picks, entry_history, subs}` |
| `fetch-live.ts` | `GET https://draft.premierleague.com/api/event/{gw}/live` for **new** GWs only | `data/live/gw{XX}.json` (per-GW per-player stats) | Yes - returns `{elements: {id: {stats: {...}}}}` with xG/xA |
| `fetch-transactions.ts` | `GET https://draft.premierleague.com/api/draft/league/820/transactions` | `data/transactions.json` (waivers, trades) | Yes - returns array of transaction objects with kind (w/f) and result (a/di/do) |
| `fetch-draft.ts` | `GET https://draft.premierleague.com/api/draft/820/choices` | `data/draft.json` (draft picks) | Yes - returns `{choices: [...]}` with 120 picks across 15 rounds |
| `fetch-fixtures.ts` | `GET https://fantasy.premierleague.com/api/fixtures/` | `data/fixtures.json` (upcoming PL fixtures for predictions) | Yes - public endpoint, no auth, returns fixture array with difficulty ratings |
| `transform.ts` | Reads all fetched JSON | `data/dashboard.json` (pre-computed dashboard data) | N/A (internal) |

**Error handling strategy (all fetch scripts):**
- Exponential backoff: retry 3x with delays of 2s, 8s, 32s
- Validate HTTP status AND response JSON structure before writing to disk
- If a fetch fails after all retries: log error, skip that endpoint, do NOT overwrite existing data file
- Transform step: check file existence and timestamps before processing. If any critical file (league.json, players.json) is missing, abort transform and fail loudly (triggers GitHub Actions failure notification). If non-critical files (draft.json, fixtures.json) are missing, generate degraded dashboard.json with explicit `dataAvailable` flags per section.

**Rate limiting:** 500ms delay between each API request. For batch fetches (picks: 8 requests per GW), add 200ms between individual requests within the batch.

### 3.2 Pre-computed Dashboard Data (`transform.ts`)

- **Responsibility:** Transform raw API data into structures optimized for dashboard rendering
- **Inputs:** All JSON files from fetch scripts
- **Outputs:** `data/dashboard.json` containing pre-computed views

**Pre-computed structures:**

```typescript
interface DashboardData {
  meta: {
    lastUpdated: string;       // ISO timestamp of last successful transform
    currentGameweek: number;
    leagueName: string;
    season: string;            // "2025-26"
    dataAvailable: {           // Flags for graceful degradation
      standings: boolean;
      picks: boolean;
      live: boolean;
      transactions: boolean;
      draft: boolean;
      fixtures: boolean;
      ownership: boolean;
    };
    fetchErrors: string[];     // List of endpoints that failed in last fetch
  };
  standings: Standing[];        // Current league table
  managers: Manager[];          // Manager profiles with aggregated stats
  gameweekHistory: GameweekSnapshot[]; // Per-GW standings for trend charts
  h2hMatrix: H2HRecord[][];    // All-vs-all head-to-head records
  playerStats: PlayerStat[];    // Top players within the league (owned)
  freeAgents: PlayerStat[];     // Best available unowned players
  powerRankings: PowerRank[];   // Team strength scores
  transactions: Transaction[];  // Waiver/trade timeline
  draftPicks: DraftPick[];      // Draft recap data
  predictions: Prediction[];    // Next GW point predictions per team (uses xG/xA from API + FDR)
  benchAnalysis: BenchData[];   // Points left on bench per manager per GW
}
```

**Note on bench analysis:** FPL Draft uses auto-substitution rules. To accurately calculate "bench points lost", the transform must simulate the substitution logic: a bench player only comes on if a starting player played 0 minutes, and substitutions follow position rules and bench order. The simpler alternative (total bench points regardless of eligibility) should be implemented first, with accurate substitution logic as a Phase 3 enhancement.

## 5. Integration Design

### 5.0 Shared Error Handling Strategy

All FPL API integrations share these behaviors:
- **Retry:** 3 attempts with exponential backoff (2s, 8s, 32s)
- **Validation:** Check HTTP status (200) AND validate response JSON has expected top-level keys
- **Failure mode:** On persistent failure, log error with endpoint name, HTTP status, and response body. Do NOT overwrite existing data file — stale data is better than no data.
- **Rate limiting:** 500ms delay between different endpoint calls. 200ms delay between requests within batch operations.
- **API instability:** The FPL API is known to return 503s during live match days. The cron is offset to 01:00/07:00/13:00/19:00 UTC to avoid peak times. Exponential backoff handles transient failures.

### 5.1 FPL Draft API — Bootstrap Static

- **System:** draft.premierleague.com
- **Protocol:** REST (GET)
- **Authentication:** None required (verified 2026-03-12)
- **Endpoint:** `GET https://draft.premierleague.com/api/bootstrap-static`
- **Response structure:** `{ elements: PlayerObject[] }` — array of 700+ player objects
- **Key fields:** `id`, `web_name`, `team`, `element_type`, `total_points`, `form`, `expected_goals`, `expected_assists`, `expected_goal_involvements`, `minutes`, `goals_scored`, `assists`, `clean_sheets`, `ict_index`
- **Data exchanged:** All players with stats including xG and xA (confirmed available in Draft API)

### 5.2 FPL Draft API — League Details

- **Endpoint:** `GET https://draft.premierleague.com/api/league/820/details` (verified 2026-03-12)
- **Response structure:** `{ league: {...}, league_entries: [...], matches: [...], standings: [...] }`
- **Data exchanged:** League config, 8 manager entries, all matches (GW1-38) with points, standings with W/D/L
- **Criticality:** HIGH — this is the core data source. If this fails, abort the entire fetch cycle.

### 5.3 FPL Draft API — Element Status

- **Endpoint:** `GET https://draft.premierleague.com/api/league/820/element-status` (verified 2026-03-12)
- **Response structure:** `{ element_status: [{ element: number, owner: number|null, status: "a"|"o", in_accepted_trade: boolean }] }`
- **Data exchanged:** Player ownership mapping — who owns which player, and which are available

### 5.4 FPL Draft API — Entry Event Picks

- **Endpoint:** `GET https://draft.premierleague.com/api/entry/{entry_id}/event/{gw}` (verified 2026-03-12)
- **Response structure:** `{ picks: [{ element, position, is_captain, is_vice_captain, multiplier }], entry_history: {}, subs: [{ element_in, element_out, event }] }`
- **Data exchanged:** Team picks for a specific manager in a specific gameweek, including auto-substitutions
- **Batch strategy:** Fetch for all 8 entries x **only new** GWs since `meta.json.lastFetchedGameweek`
- **Initial seed:** For first run (GW1-29), fetch progressively: 8 requests per GW with 200ms delay between requests, 1s delay between GWs. Total ~232 requests over ~5 minutes.
- **Incremental:** After seed, only 8 new requests per completed GW
- **Output:** `data/picks/gw{XX}.json` — one file per gameweek containing all 8 entries' picks. Completed GW files are immutable.

### 5.5 FPL Draft API — Live Event Stats

- **Endpoint:** `GET https://draft.premierleague.com/api/event/{gw}/live` (verified 2026-03-12)
- **Response structure:** `{ elements: { [id]: { stats: { minutes, goals_scored, assists, ..., expected_goals, expected_assists, total_points } } } }`
- **Data exchanged:** Per-player stats for a specific gameweek including xG/xA
- **Incremental:** Only fetch GWs since `meta.json.lastFetchedGameweek`. Current/in-progress GW is re-fetched on every cycle.
- **Output:** `data/live/gw{XX}.json` — one file per gameweek. Completed GW files are immutable.

### 5.6 FPL Draft API — Transactions

- **Endpoint:** `GET https://draft.premierleague.com/api/draft/league/820/transactions` (verified 2026-03-12)
- **Response structure:** Array of `{ id, entry, event, element_in, element_out, kind: "w"|"f", result: "a"|"di"|"do", priority, index }`
- **Data exchanged:** All waiver requests and free agent pickups with approval/rejection status
- **Note:** `kind: "w"` = waiver request, `kind: "f"` = free agent pickup. `result: "a"` = accepted, `"di"` = rejected (higher priority claim), `"do"` = rejected (other)

### 5.7 FPL Draft API — Draft Choices

- **Endpoint:** `GET https://draft.premierleague.com/api/draft/820/choices` (verified 2026-03-12)
- **Response structure:** `{ choices: [{ round, pick, element, entry, entry_name, player_first_name, player_last_name, was_auto, choice_time }] }`
- **Data exchanged:** Complete draft history — 120 picks across 15 rounds for 8 teams
- **Optimization:** Fetch once (check `meta.json.draftFetched`). Draft is immutable after completion.

### 5.8 Regular FPL API — Fixtures

- **Endpoint:** `GET https://fantasy.premierleague.com/api/fixtures/` (verified 2026-03-12 — public, no auth)
- **Data exchanged:** All Premier League fixtures with dates, teams, difficulty ratings
- **Used for:** Point predictions — fixture difficulty ratings inform expected points calculations
- **Note:** This is the regular FPL API, not the Draft API. Same CORS restrictions apply but irrelevant since we fetch server-side.

## 6. Security Design

This is a read-only public dashboard with no user input, no authentication, and no personal data. Security scope is minimal but addressed:

- **No authentication:** Dashboard is public. No login, no sessions, no cookies.
- **No user input:** No forms, no search, no query parameters that touch a backend. Zero XSS surface.
- **No secrets in client code:** API calls happen in GitHub Actions (server-side). No API keys or tokens in the frontend.
- **GitHub Actions secrets:** None needed — API is public. If auth becomes required, a session cookie could be stored as a GitHub Actions secret.
- **Data sensitivity:** Only public fantasy league data. Player names in the league are already public on the FPL Draft platform. No PII beyond fantasy team names and first names.
- **GDPR:** Not applicable — no data collection from visitors, no analytics, no cookies, no tracking.
- **Content Security Policy:** Standard GitHub Pages CSP. No inline scripts needed.
- **Dependency supply chain:** Use `npm audit` in CI. Pin major versions. Astro and Chart.js are well-maintained projects with large communities.

### 7.2 CI/CD Pipeline Design

**IMPORTANT:** GitHub Actions commits using `GITHUB_TOKEN` do NOT trigger subsequent workflows. This means a separate "fetch" workflow that commits data would never trigger a separate "deploy" workflow. The solution is a **single combined workflow** for the data pipeline + build + deploy.

**Workflow 1: `fetch-and-deploy.yml` — Data Pipeline + Build + Deploy**
```yaml
name: Fetch Data & Deploy
on:
  schedule:
    - cron: '0 1,7,13,19 * * *'  # 01:00, 07:00, 13:00, 19:00 UTC
                                    # Offset from PL kickoff times to avoid API instability
  workflow_dispatch:                # Manual trigger for live GW updates
permissions:
  contents: write                   # Push data commits
  pages: write                      # Deploy to GitHub Pages
  id-token: write                   # Required for Pages deployment
jobs:
  fetch-build-deploy:
    runs-on: ubuntu-latest
    steps:
      - Checkout repo
      - Setup Node.js 22
      - Install dependencies
      - Run fetch-all.ts (fetches all API endpoints with incremental caching)
      - Run transform.ts (builds dashboard.json with validation)
      - Check if data changed (git diff --quiet data/)
      - If changed: commit & push data files to main
      - Build Astro site (astro build) — always runs, even if data unchanged
      - Deploy to GitHub Pages (actions/deploy-pages)
```

**Workflow 2: `deploy-on-code-change.yml` — Code-Only Deploy**
```yaml
name: Deploy on Code Change
on:
  push:
    branches: [main]
    paths: ['src/**', 'astro.config.*', 'package.json', 'tailwind.config.*']
    # NOTE: Excludes data/** because data changes are handled by Workflow 1
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - Checkout repo
      - Setup Node.js 22
      - Install dependencies
      - Build Astro site (astro build)
      - Deploy to GitHub Pages (actions/deploy-pages)
```

**Workflow 3: `keepalive.yml` — Prevent Cron Disable**
```yaml
name: Keepalive
on:
  schedule:
    - cron: '0 12 * * 1'  # Every Monday at noon UTC
jobs:
  keepalive:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Keepalive to prevent GitHub from disabling scheduled workflows"
```
This prevents the 60-day inactivity timeout that would otherwise disable the data pipeline during the off-season (June-August). Cost: ~0 minutes/week (near-instant job).
